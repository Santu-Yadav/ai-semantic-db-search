# Phase 6.2 — Better Chunking

## Goal

Improve how documents are split into chunks before generating embeddings.

The goal was to understand chunk size, overlap, and chunk boundaries, then replace manually created chunks with automatically generated chunks.

## 1. Why Chunking?

A large document should be split into smaller pieces before embedding.

```text
Document
   ↓
Chunks
   ↓
Embeddings
   ↓
Vector Search
   ↓
Relevant Chunks
   ↓
RAG
```

Chunking determines the pieces of knowledge available to retrieval.

## 2. Chunk Size

We learned that chunk size controls approximately how much text belongs in each chunk.

Example:

```ts
chunkText(text, 80, 20);
```

- `80` = approximate target chunk size
- `20` = approximate overlap

Smaller chunks can provide focused retrieval but less context.

Larger chunks provide more context but may contain unrelated information.

There is no universal perfect chunk size.

## 3. Initial Fixed-Character Chunking

The first implementation used:

```ts
text.slice(start, end);
```

This split text every N characters and could split words:

```text
"React is a JavaScript library for building user in"
"ng user interfaces..."
```

This is simple but not ideal for RAG.

## 4. Chunk Overlap

Overlap means neighboring chunks share some content.

```text
Chunk 1
[--------------------]

        Chunk 2
        [--------------------]
```

Overlap helps preserve context when an idea crosses a chunk boundary.

## 5. Problem with Character-Based Overlap

Initially we used:

```ts
currentChunk.slice(-overlap);
```

This could create overlap such as:

```text
"ng user interfaces."
```

The overlap could start in the middle of a word.

## 6. Word-Safe Overlap

We changed the implementation to build overlap from complete words.

Instead of:

```text
"ng user interfaces."
```

we get:

```text
"user interfaces."
```

So the current approach uses:

```text
Sentence-aware chunks
+
Word-safe overlap
```

## 7. Sentence-Aware Chunking

We changed the chunker to split the document into sentences first.

The implementation recognizes sentence boundaries such as:

```text
.
!
?
```

Sentences are combined until adding another sentence would exceed the target size.

Therefore chunk size is a **soft target**, not a strict maximum.

For example, with a target of 80 characters, we observed:

```text
59 characters
95 characters
101 characters
```

This is intentional because we prefer keeping sentences intact rather than breaking them at an exact character position.

## 8. Chunking Utility

File:

```text
src/lib/chunk-text.ts
```

The utility provides:

```ts
chunkText(text, chunkSize, overlap);
```

It:

1. Splits text into sentences.
2. Builds chunks around the target size.
3. Preserves sentence boundaries.
4. Adds word-safe overlap.
5. Returns an array of chunks.

## 10. Integrating Chunking into RAG Ingestion

Previously, `seed-rag.ts` manually contained the chunk array.

We changed it so the seed script contains document content and generates chunks automatically:

```text
Document content
      ↓
chunkText()
      ↓
chunkContents[]
      ↓
Prisma
      ↓
Document + Chunk records
```

File:

```text
prisma/seed-rag.ts
```

We no longer need to manually maintain every chunk.

## 11. Embedding the New Chunks

After generating chunks, we ran:

```text
POST /api/ingest
```

The flow is:

```text
Existing chunks
      ↓
Gemini gemini-embedding-001
      ↓
3072-dimensional embeddings
      ↓
Chunk.embedding
```

The embeddings were successfully stored in PostgreSQL/Neon using pgvector.

## 12. Retrieval Test

We tested:

```text
How does React manage changing data?
```

The relevant state chunk was ranked first, with distance around:

```text
0.1008
```

This showed that the new chunking strategy still allowed relevant information to be retrieved.

## 13. Retrieval Test Set

We tested:

```text
What is React?
What are React props?
How does React state work?
What are React Hooks?
What is the difference between useMemo and useCallback?
```

The relevant chunks appeared at or near the top.

For the Hooks query, the Hooks definition was #1, followed by related `useState` and `useEffect` chunks.

For the `useMemo` vs `useCallback` query:

```text
chunk 8 → useCallback
chunk 7 → useMemo
```

Both relevant chunks were retrieved near the top.

## 14. Full RAG Test

We tested:

```text
What is the difference between useMemo and useCallback?
```

Vector search retrieved the `useCallback` and `useMemo` chunks.

RAG passed them to Gemini, which generated the grounded comparison:

```text
useCallback → memoizes a function/reference
useMemo     → memoizes a calculated value
```

This demonstrated that the new chunks work through the complete RAG pipeline.

## 15. Important Learning: Retrieval Depends on Available Knowledge

During testing, we temporarily reduced the knowledge base to three chunks.

Queries about Hooks, useMemo, and useCallback could not retrieve those concepts.

This was not a chunking failure. The relevant knowledge simply did not exist in the database.

Important principle:

```text
Vector search can only retrieve information
that exists in the knowledge base.
```

```text
Document
   ↓

   ↓
Word-safe overlap
   ↓

   ↓

   ↓
pgvector
   ↓
Vector Search
   ↓
Retrieved chunks

   ↓
Grounded answer
```

## 17. What We Learned

- **Chunk size:** controls approximately how much information each chunk contains.
- **Chunk overlap:** provides shared context between neighboring chunks.
- **Sentence-aware boundaries:** avoid breaking sentences unnecessarily.
- **Word-safe overlap:** avoids overlap starting in the middle of a word.
- **Soft chunk-size limit:** sentence boundaries can make chunks larger than the target.
- **Automatic chunk generation:** documents can now be converted into chunks programmatically.
- **Retrieval validation:** the new chunks successfully retrieved relevant information for our test queries.
