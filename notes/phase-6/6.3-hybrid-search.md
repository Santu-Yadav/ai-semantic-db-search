## 1. What is Hybrid Search?

Hybrid search combines two different retrieval approaches:

1.  **Keyword search** --- finds documents based on matching words or
    terms.
2.  **Vector search** --- finds documents based on semantic meaning.

The goal is to get the strengths of both approaches.

``` text
User Query
    ↓
 ┌───────────────┐
 │               │
 ↓               ↓
Keyword Search  Vector Search
 │               │
 └───────┬───────┘
         ↓
   Combine Rankings
         ↓
        RRF
         ↓
  Hybrid Results
```

------------------------------------------------------------------------

## 2. Why Do We Need Hybrid Search?

### Keyword search

Keyword search is good when the user uses an exact technical term.

Example:

``` text
useMemo
```

If the knowledge base contains:

``` text
The useMemo Hook memoizes a calculated value...
```

keyword search can find it directly.

### Vector search

Vector search is good when the user describes a concept using different
words.

Example:

``` text
How can I reuse a calculated value between renders?
```

The query may not contain the exact term `useMemo`, but vector search
can understand the semantic relationship.

### Hybrid search

Hybrid search combines both.

``` text
Keyword search
    +
Vector search
    ↓
Better retrieval
```

------------------------------------------------------------------------

## 3. Keyword Search in Our Project

Our keyword search uses PostgreSQL full-text search.

Important PostgreSQL functions/operators:

``` sql
to_tsvector()
plainto_tsquery()
@@
ts_rank()
```

Example:

``` sql
SELECT
  "id",
  "content",
  ts_rank(
    to_tsvector('english', "content"),
    plainto_tsquery('english', ${query})
  ) AS rank
FROM "Chunk"
WHERE
  to_tsvector('english', "content")
  @@ plainto_tsquery('english', ${query})
ORDER BY rank DESC
LIMIT 5
```

### Important points

`to_tsvector()`:

-   converts document text into searchable terms.

`plainto_tsquery()`:

-   converts the user's normal text query into a PostgreSQL search
    query.

`@@`:

-   checks whether the document matches the query.

`ts_rank()`:

-   calculates a relevance score for matching documents.

For keyword search:

``` text
Higher rank = better match
```

------------------------------------------------------------------------

## 4. Vector Search in Our Project

Vector search uses:

``` text
Gemini
   ↓
Query embedding
   ↓
pgvector
   ↓
Similarity/distance calculation
   ↓
Nearest chunks
```

Our embedding model:

``` text
gemini-embedding-001
```

The embedding has 3072 dimensions.

The query embedding is compared against the stored chunk embeddings
using pgvector.

We use:

``` sql
"embedding" <=> ${vector}::vector
```

`<=>` represents cosine distance.

For cosine distance:

``` text
Lower distance = more similar
```

------------------------------------------------------------------------

## 5. Why We Cannot Directly Add the Scores

Keyword search produces a `ts_rank` score.

Vector search produces a cosine distance.

They have different meanings and scales.

For example:

``` text
Keyword:
rank = 0.18

Vector:
distance = 0.15
```

We cannot simply do:

``` text
0.18 + 0.15
```

because the two numbers are not directly comparable.

Instead, we combine the **ranking positions**.

This is where RRF is used.

------------------------------------------------------------------------

## 6. Reciprocal Rank Fusion (RRF)

RRF stands for:

**Reciprocal Rank Fusion**

It combines rankings from multiple search systems.

Our formula is:

``` text
RRF score = 1 / (k + rank)
```

Our implementation uses:

``` ts
const RRF_K = 60;
```

Therefore:

``` text
rank 1 → 1 / 61
rank 2 → 1 / 62
rank 3 → 1 / 63
```

Higher-ranked results receive a larger contribution.

------------------------------------------------------------------------

## 7. Why RRF Works Well

Suppose a chunk appears:

``` text
Vector search:
rank 1

Keyword search:
rank 1
```

Its RRF score is:

``` text
1 / 61 + 1 / 61

= 0.032786...
```

That chunk receives evidence from **both retrieval systems**, so it
rises to the top.

If a chunk appears only at rank 2 in one system:

``` text
1 / 62

= 0.016129...
```

Therefore:

``` text
Appears highly in both
        ↓
Higher combined score
        ↓
Higher hybrid ranking
```

## 8. Our Hybrid Search Implementation

The reusable implementation is:

``` text
src/lib/hybrid-search.ts
```

It exposes:

``` ts
hybridSearch(query)
```

The function:

1.  Generates the query embedding.
2.  Runs vector search.
3.  Runs keyword search.
4.  Combines the rankings using RRF.
5.  Sorts by RRF score.
6.  Returns the top 5 results.

Vector and keyword searches run in parallel:

``` ts
const [vectorResults, keywordResults] = await Promise.all([
  // vector search
  // keyword search
]);
```

This allows both retrieval operations to execute concurrently.

------------------------------------------------------------------------

## 9. Why `Map` Is Used

The hybrid search uses a JavaScript `Map`:

``` ts
const results = new Map();
```

The chunk ID is used as the key.

Example:

``` text
"react-chunk-7"
      ↓
{
  id: "react-chunk-7",
  rrfScore: ...,
  vectorRank: 1,
  keywordRank: 1
}
```

This is useful because the same chunk may appear in both searches.

When the chunk appears in the second search, we can find the existing
result:

``` ts
const existing = results.get(result.id);
```

and add the second RRF contribution.

------------------------------------------------------------------------

## 10. `results.values()`

At the end, the Map contains:

``` text
key → result object
```

For example:

``` text
react-chunk-7  → result object
react-chunk-8  → result object
react-chunk-10 → result object
```

``` ts
results.values()
```

returns the values stored in the Map.

It returns an iterator, not an array.

Therefore:

``` ts
Array.from(results.values())
```

converts those values into an array.

Then we can use array methods:

``` ts
Array.from(results.values())
  .sort((a, b) => b.rrfScore - a.rrfScore)
  .slice(0, TOP_K);
```

This means:

``` text
Map values
   ↓
Array
   ↓
Sort by RRF score
   ↓
Take top 5
```

## 11. Hybrid Search API

The API route is:

``` text
src/app/api/hybrid-search/route.ts
```

The route is intentionally thin.

It receives the query and calls:

``` ts
const results = await hybridSearch(query);
```

The actual retrieval logic lives in:

``` text
src/lib/hybrid-search.ts
```

This makes the retrieval logic reusable.

``` text
                 hybridSearch()
                      ↑
              ┌───────┴────────┐
              │                │
/api/hybrid-search       /api/rag-search
```

An API route should not need to call another API route internally just
to reuse retrieval logic.

## 13. What Hybrid Search Does in Our Project

Hybrid search is responsible for:

``` text
Finding relevant knowledge
```

It does **not** generate the final answer.

The responsibilities are:

``` text
Hybrid Search
    ↓
Retrieve relevant chunks
```

Then:

``` text
RAG
    ↓
Take retrieved chunks
    ↓
Build context
    ↓
Send context + question to Gemini
    ↓
Generate grounded answer
```

## 15. What Hybrid Search Does NOT Do

Hybrid search does not:

-   generate the final answer
-   create embeddings for documents
-   create documents
-   create chunks
-   store embeddings
-   replace Gemini generation
-   replace RAG
-   guarantee that every retrieved result is relevant

Responsibilities remain separated:

``` text
Chunking
    → creates chunks

Gemini embedding model
    → creates embeddings

pgvector
    → stores embeddings and performs vector comparison

Keyword search
    → finds lexical matches

Hybrid search
    → combines keyword + vector retrieval

RAG
    → retrieves context + generates an answer

Gemini generation model
    → generates the final response
```

## 17. Current Limitation / Next Phase

Hybrid search improves retrieval, but it does not guarantee that the
best chunk is ranked first.

For example, with:

``` text
React state
```

a semantically related chunk can sometimes rank above the chunk that
directly explains React state.

The next retrieval-quality improvement is:

``` text
Phase 6.4 — Re-ranking
```

The idea is:

``` text
Hybrid Search
      ↓
Candidate chunks
      ↓
Re-ranker
      ↓
Better final ordering
      ↓
RAG generation
```
