# Phase 6.4 — Re-ranking

## Goal

Improve retrieval relevance by reordering candidate chunks from hybrid search before they are passed to the grounded answer-generation step.

## Pipeline

1. **Hybrid search** retrieves candidate chunks using semantic vector search and keyword search, combining their rankings with Reciprocal Rank Fusion (RRF).
2. **Re-ranking** sends the user's query and candidate chunk IDs/content to Gemini.
3. Gemini returns the chunk IDs ordered from most relevant to least relevant.
4. The application maps those IDs back to the original chunk objects, preserving their content and metadata.
5. **Grounded generation** builds context from the re-ranked chunks and asks Gemini to answer using that context.

```text
User query
   ↓
Hybrid search (vector + keyword + RRF)
   ↓
Candidate chunks
   ↓
Gemini re-ranking
   ↓
Re-ranked chunks
   ↓
Grounded answer generation
   ↓
Answer + re-ranked sources
```

## Implementation

- Added `src/lib/rerank-chunks.ts` with the `rerankChunks(query, chunks)` function.
- The function asks `gemini-3.6-flash` to return a JSON array of chunk IDs in relevance order.
- It validates that the response contains every input chunk ID exactly once.
- It reconstructs the ordered result from the original chunk objects, preserving metadata such as `rrfScore`, `distance`, `vectorRank`, and `keywordRank`.
- If there are fewer than two chunks, the function returns them unchanged.
- If the Gemini request fails or the response is invalid, the function logs the failure and falls back to the original hybrid-search order. This keeps the RAG pipeline usable when re-ranking is unavailable, but it means re-ranking did not succeed for that request.

## RAG API integration

Updated `src/app/api/rag-search/route.ts` to:

1. Call `hybridSearch(query)`.
2. Pass its results to `rerankChunks(query, chunks)`.
3. Build the generation context from `rerankedChunks`.
4. Return `rerankedChunks` in the response's `sources` field.

The existing hybrid-search implementation remains unchanged.

## Limitations and follow-up

- Re-ranking can only reorder retrieved candidates; it cannot recover relevant chunks that hybrid search did not retrieve.
- This implementation reranks the five candidates returned by the current hybrid search.
- A changed order demonstrates that re-ranking ran, but does not by itself prove improved retrieval quality. Phase 6.7 evaluation should compare retrieval and answer quality across a repeatable set of queries.
- Re-ranking adds another Gemini generation request, increasing latency and exposure to transient API errors.
- The fallback preserves availability but leaves the hybrid order in place for that request, apart from the server log. Consider exposing re-ranking status in development diagnostics if needed.
